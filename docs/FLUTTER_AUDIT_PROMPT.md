# Flutter 项目架构与性能审计 · 主控 Prompt

用法：把本文件第 2 节（"可直接粘贴的 Prompt"）整段复制进对话，替换最后的项目路径。
配套文件：同目录 `flutter-audit-checklist.md`，拷到项目的 `docs/` 下供 AI 读取。

---

## 1. 为什么这样写

直接问"帮我分析这个项目有什么优化点"，失败在这几处：

| 失败点 | 后果 | 本方案的解法 |
|---|---|---|
| 没有全局视角，只抽样读几个文件 | 结论基于 10% 代码，剩下 90% 靠脑补 | Stage 0 强制先产出项目地图，把"事实"和"判断"拆开 |
| 没有基线数字 | "可以优化"无法验证，改完也不知道有没有用 | Stage 1 先量 analyze / 包体积 / 帧耗时 |
| 一次给 50 条建议 | 你执行不了，AI 也执行不了 | Stage 3 定级排序 + 你拍板前 5 项 |
| 不给规则集 | 只会复述教科书，抓不到本项目真实热点 | 外挂 checklist 作为检查维度，逼它逐维度过一遍 |
| 不要求证据 | 幻觉出不存在的方法名、包名、行号 | 铁律要求 file:line + 代码片段，不确定的单独列"待确认" |

核心结构是**三层分离**：事实层（地图/基线）→ 判定层（问题清单/定级）→ 行动层（逐项改+回归）。

## 2. 可直接粘贴的 Prompt

```
# 任务：Flutter 项目架构与性能审计，分阶段执行

## 角色
你是资深 Flutter 架构师 + 性能工程师。目标不是"多给建议"，而是产出可执行、可验证、有证据的改进清单，并逐项落地。

## 铁律
1. 先建事实，再下判断。Stage 0 未完成前，禁止提出任何优化建议。
2. 每条结论必须给出真实文件路径 + 行号 + 关键代码片段。找不到证据的推测放进"待确认"，不要混进结论。
3. 禁止编造 API、包名、配置项、lint 规则名。不确定就 grep 或读文件确认。
4. 禁止一次性大规模重构。所有改动按 P0/P1/P2 分级，我确认后逐项执行。
5. 不评价纯风格偏好（缩进、命名习惯），除非违反项目已有 lint 规则。
6. 每条建议要写清"不改会怎样"，而不只是"改了更好"。

## Stage 0：项目地图（只描述，不评价，不优化）
产出 ARCHITECTURE.md：
- 技术栈：Flutter/Dart 版本、状态管理方案、路由方案、网络库、本地存储、主要三方依赖及各自用途
- 目录结构与分层：是否存在 data/domain/presentation 或类似分层；哪些文件跨层引用（列出具体引用位置）
- 启动链路：main → 初始化了什么 → 首屏渲染前发生了什么阻塞操作
- 页面清单：路由路径、文件、行数、职责一句话
- 规模热点：代码行数 Top 20 文件（不含生成代码）
- 依赖健康度：pubspec 中声明但全项目无 import 的包（逐个 grep 验证后列出）
- 构建配置：flavor / 混淆 / tree-shake-icons / split-debug-info / 目标平台
禁止在此阶段写"建议"。

## Stage 1：基线测量
能跑就跑，跑不了就明确标注"未测量"，禁止估算：
- flutter analyze 结果（error/warning/info 各多少条）
- 包体积：flutter build apk --analyze-size（或 ios --analyze-size）
- 性能：profile 模式下的长帧位置、明显卡顿场景（若无法运行，标注需我提供 DevTools 截图）
- 测试现状：test/ 目录存在与否、能覆盖多少
产出 BASELINE.md。此后任何没有基线支撑的收益判断，一律标注"收益不确定"。

## Stage 2：按规则集体检
优先读取 docs/flutter-audit-checklist.md 作为检查维度并逐项过一遍。
若该文件不存在，按以下维度自查：架构分层 / 状态管理粒度 / Widget 重建 / 列表与渲染 / 图片与资源 / 异步与 isolate / 网络与缓存 / 启动与包体积 / 代码复杂度 / 测试与质量门禁。
每条问题输出为一行表格：
| ID | 维度 | 严重度 | 文件:行 | 问题描述 | 证据片段 | 修法 | 预期收益 | 置信度 |
严重度定义：P0 = 明显浪费或崩溃风险；P1 = 高频路径性能；P2 = 架构债；P3 = 风格。
置信度：高（有代码证据）/ 中（有模式特征但需运行验证）/ 低（推测，需人工确认）。

## Stage 3：排序与确认（必须停下来等我）
按"影响面 × 置信度 ÷ 改动成本"排序，给出建议优先做的前 5 项，每项说明改完能解决什么。
我确认后进入 Stage 4。

## Stage 4：逐项实施
一次只处理一个 ID。固定流程：改代码 → flutter analyze → dart format → 跑相关测试 → 在 CHANGELOG 记录该 ID 的改动摘要。
禁止顺手改无关代码。改完立刻回到清单取下一项，不要问我"要不要继续"。
遇到需要我决策的设计选择（如换状态管理库），停止该项并写入 BLOCKERS.md，跳过继续下一项。

## Stage 5：回归验证
重跑 Stage 1 全部基线，输出前后对比表：analyze 数量、包体积、关键页面帧耗时。

## 现在开始
项目根目录：<填绝对路径>
从 Stage 0 开始。Stage 0 + Stage 1 + Stage 2 是只读分析，可以连续跑完再汇报；到 Stage 3 必须停下来等我确认。
```

## 3. 三个检查点设计

不要把"一口气全做完"当成目标。审计任务里，方向错了后面全废：

| 检查点 | 位置 | 为什么必须停 |
|---|---|---|
| 停点 1 | Stage 3 结束 | 优先做哪几项要你来定，AI 不知道你的发版节奏和风险偏好 |
| 停点 2 | 每项 Stage 4 完成后 | 逐项可回滚，出问题能定位到具体 ID |
| 停点 3 | Stage 5 | 用数字验收，而不是听它说"已优化" |

Stage 0~2 可以连续跑，属于只读操作，正是上一个话题里"一直往下做"的适用场景。

---

## 4. 提高命中率的三个小技巧

1. **锁版本**：明确告诉它 Flutter 和 Dart 版本，不同版本 API 和最佳实践差异很大（如 Impeller、Records、const 优化）。
2. **给它热点**：如果你知道哪几个页面卡，直接点名。AI 从热点出发找根因，比全项目扫描精准得多。
3. **先量后改**：包体积和帧耗时是唯一能证伪的指标。没有这两个数字，所有"性能提升"都是话术。

---

## 5. 常见翻车方式

- 让它"顺手优化一下"某个文件：会连带重写逻辑，diff 巨大且不可 review
- 允许它跳过 analyze：一改就红，后面全在修编译错误
- 一次性让它在 30 个文件里加 const：看似安全，实际淹没真实问题
- 不给严重度标准：它会把"命名不规范"和"列表未用 builder"并列输出
