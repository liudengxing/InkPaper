# ROADMAP 规范 · 让 AI 沿着路线图自己往下做

配套文件：`FLUTTER_AUDIT_PROMPT.md`（怎么产出 finding）、`ROADMAP.template.md`（可直接抄的骨架）

---

## 0. 一句话原则

**一条任务如果需要人来判断"算不算做完"，AI 就一定会在那里停下来问你。**

所以 roadmap 不是为了"记录你想做什么"，是为了让 AI 能**独立判断下一步做什么、做完没做完**。

---

## 1. 状态三件套

放在项目根目录，各管一件事，不要合并：

| 文件 | 作用 | 谁写 | 特征 |
|---|---|---|---|
| `ROADMAP.md` | 任务清单 + 每条任务的完整定义 | 人定框架，AI 勾状态 | 唯一真相，AI 每轮先读 |
| `PROGRESS.md` | 每轮执行日志 | AI 只 append | 只增不改，用于恢复现场 |
| `BLOCKERS.md` | 需要人决策的事 | AI 写入，你清空 | AI 的合法掉头通道 |

为什么必须分开：`ROADMAP.md` 需要保持简洁可解析（AI 每轮都读），日志会越写越长，混在一起会让上下文迅速膨胀。

---

## 2. 任务条目必须满足的 6 个条件

不满足就别写进 roadmap，或者先拆细。

| # | 条件 | 反例 | 正例 |
|---|---|---|---|
| 1 | **单一交付物**：一个能说清的作用域 | "重构状态管理" | "把 auth 模块的 3 个 setState 迁到 AuthNotifier" |
| 2 | **机器可验证**：验收是命令 + 期望结果 | "代码更清晰" | `rg "setState" lib/features/auth` 结果为 0 |
| 3 | **作用域封闭**：明确允许改哪些文件 | "优化首页性能" | `lib/features/home/**`、`assets/images/home_*.webp` |
| 4 | **前置明确**：依赖哪些任务先完成 | 无 | blockedBy: `ARCH-STATE-003` |
| 5 | **可回滚**：出问题怎么退回 | 无 | 单 commit，`git revert <sha>` 即可 |
| 6 | **禁止顺手**：明确列出不许碰的东西 | 无 | 不许改路由结构、不许动 API 层 |

第 6 条最容易被忽略，也最容易造成"改一个文件，diff 八百行"。

## 3. ID 与状态机

**ID 格式：`<分类前缀>-<子类>-<三位序号>`**

| 前缀 | 含义 | 来源维度 |
|---|---|---|
| `ARCH` | 架构分层、依赖方向 | checklist 第 1 节 |
| `STATE` | 状态管理与订阅粒度 | 第 2 节 |
| `PERF` | Widget 重建、渲染开销 | 第 3 节 |
| `LIST` | 列表与滚动 | 第 4 节 |
| `IMG` | 图片与资源 | 第 5 节 |
| `ASYNC` | 异步、isolate、防抖 | 第 6 节 |
| `NET` | 网络与缓存 | 第 7 节 |
| `BUILD` | 启动与包体积 | 第 8 节 |
| `QUAL` | 复杂度、lint、测试 | 第 9-10 节 |

规则：**ID 一旦分配，永不复用、永不重排**。删掉的任务保留条目并把状态改成 `dropped`，否则你过两个月会搞不清 `PERF-007` 到底是不是漏了。

**状态只有五个，禁止中间态：**

```
todo → doing → done
        ├→ blocked   （写进 BLOCKERS.md，等 人 决策）
        ├→ skipped   （不做了，写原因）
        └→ dropped   （条目作废）
```

`doing` 只允许一条同时存在。这条约束很关键——它让"现在在干什么"永远无歧义，上下文被压缩也不会乱。

## 4. 条目字段表

| 字段 | 必填 | 说明 |
|---|---|---|
| ID | 是 | 见上 |
| 标题 | 是 | 动词开头，一句话，不超 20 字 |
| 优先级 | 是 | P0 / P1 / P2 / P3 |
| 前置 | 否 | 被 block 的 ID 列表 |
| 作用域 | 是 | 允许改的路径 glob |
| 现状证据 | 是 | `file:line` + 代码片段，来自审计 |
| 做什么 | 是 | 具体改法，不是"优化一下" |
| 验收 | 是 | 命令 + 期望输出，可复制执行 |
| 收益 | 是 | 有基线数字就写数字，没有写"未测量" |
| 回滚 | 是 | 一句话 |
| 不许做 | 是 | 顺手改动的禁区 |
| 状态 | 是 | 五态之一 |

## 5. 审计 finding → roadmap 任务的转换规则

这是把上一轮的审计产出接进 roadmap 的关键一步。**不要直接把 finding 表贴进 roadmap**，要转。

| 转换动作 | 规则 |
|---|---|
| finding 的「文件:行 + 证据」 | 原样搬进任务的「现状证据」，这是防止 AI 幻觉的锚点 |
| finding 的「修法」 | **必须改写成可执行验收命令**，不能保留自然语言 |
| finding 的「严重度」 | P0/P1/P2 各成一条任务；**P3 全部合并成一个 `QUAL-CLEAN-001` 批次任务** |
| finding 的「维度」 | 决定 ID 前缀 |
| finding 的「预期收益」 | 有基线数字填数字，没有就写"未测量，见 BASELINE.md" |
| 多个 finding 同一文件同一根因 | 合并成一条，避免 AI 在同一处反复改 |

**修法 → 验收 的改写对照：**

| 模糊修法（审计原话） | 可执行验收 |
|---|---|
| 改用 ListView.builder | `rg -c "ListView\(" lib/features/home/` 期望 0；1000 条数据滚动无长帧 |
| 拆成大 Widget 小 Widget | 目标文件行数 < 400；`flutter analyze` issue 数 ≤ 改动前 |
| 补 const | `flutter analyze` 中 prefer_const_constructors 从 N 条降到 0 |
| 压缩图片资源 | assets 图片总体积 ≤ X MB；首屏冷启动时间不劣化 |
| 状态从页面下沉 | `rg "setState" lib/features/auth/` 期望 0；登录态变更后仅 AuthScope 子树重建 |
| 加超时 | `rg "receiveTimeout" lib/core/network/` 期望 ≥ 1 处 |

验收写不出来，说明这条任务还不该进 roadmap——先补测量。

## 6. 阶段划分与退出条件

阶段的意义：给"一直做下去"设关卡，否则 AI 会在阶段边界处停下来问"接下来做什么"。

| 阶段 | 内容 | 退出条件（AI 自行判断，不许问） |
|---|---|---|
| Phase 1 止血 | 全部 P0 | ROADMAP 中 P0 条目状态均为 done/skipped/dropped |
| Phase 2 性能 | P1 高频路径 | 同上，且 `flutter build --analyze-size` 已重跑并记录 |
| Phase 3 架构 | P2 分层与状态管理 | 同上，且 `flutter analyze` 无新增 issue |
| Phase 4 收尾 | P3 合并批次 + 质量门禁 | 全部条目终结，`flutter analyze` 为 0 error |

**退出条件是自动判定**，写清楚这点，AI 才不会在阶段边界礼貌性停顿。

## 7. 自动推进：循环合约

把下面这段放在 `ROADMAP.md` 最顶部（AI 每轮必然读到）：

```
## 执行合约（每次开工必读，优先级高于其他一切）

1. 我先读 ROADMAP.md，找到状态为 doing 的条目；没有则取第一条 todo 且前置已全部 done 的条目。
2. 只加载该条目的「作用域」内文件，不重读全项目。
3. 完成后按条目里的「验收」实际执行命令，粘贴真实输出到 PROGRESS.md。
4. 验收通过 → 状态改 done → 立刻取下一项，不汇报、不询问。
5. 验收不通过 → 尝试修复，同一任务最多尝试 2 次；仍失败则状态改 blocked，
   写入 BLOCKERS.md（含已尝试方案和具体报错），然后跳过继续下一项。
6. 禁止：中途总结进度、询问"是否继续"、顺手改作用域外代码、跳过验收命令。
7. 唯一允许输出文字汇报的时机：全部条目终结，或连续 3 条 blocked。
```

第 5 条是核心——**给 AI 一条合法的失败通道**。没有它，AI 一卡住就只能停下来问你，这是最常见的停点。

### 外层驱动（三选一）

| 方式 | 适用 | 做法 |
|---|---|---|
| 定时唤醒 | 想让它在你睡觉时推进 | 建定时任务，prompt 一句话："按 ROADMAP.md 执行合约推进，本轮最多 3 条任务" |
| while 循环 | 自己写脚本跑 | 每轮独立会话，状态全靠文件传递，天然免疫上下文膨胀 |
| 手动续跑 | 想盯着 | 每轮结束只回一个字"继续"，不要回答它的问题（除非它在 BLOCKERS.md 里写了） |

关键：**每次唤醒都要设「本轮任务数上限」**。不设上限，一轮跑太久质量会下滑，而且出了错你难以定位是哪一条改崩的。

## 8. 哪些地方必须停

前一个话题说"让它一直做"，但 roadmap 推进不是全自动。这些点必须人拍板：

| 停点 | 为什么 |
|---|---|
| Phase 边界 | 决定了要不要继续投入，尤其 Phase 2→3 涉及重构风险 |
| 任何 `blocked` 累积到 3 条 | 说明有系统性问题，继续做也是白做 |
| 涉及依赖变更（pubspec 增删） | 影响包体积、许可证、构建时间，不能自动决定 |
| 涉及数据迁移 / 本地存储 schema | 不可回滚 |
| 验收命令跑不了（环境问题） | AI 容易转而"凭感觉判断完成"，必须人工确认 |

---

## 9. 常见翻车方式

- **任务粒度太粗**："优化性能"这种条目，AI 会做一半然后开始写总结
- **验收写成主观**："代码更清晰"——它完成后你没法验收，只能信它
- **一条任务跨 3 个模块**：diff 大、review 难、出问题定位不到
- **允许它顺手改**：一个 `PERF` 任务最后动了路由和网络层
- **没定义阶段退出条件**：它在 Phase 1 做完后停下来问"接下来做 Phase 2 吗"
- **PROGRESS.md 不记真实命令输出**：过一周你无法判断"验收到底跑没跑"
